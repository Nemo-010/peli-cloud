# First-party verification: SSH into a sealed sandbox over an outbound relay

**Date:** 2026-10-02
**Host:** the errand sandbox (Artix/glibc, uid 966, `bind=unix`, no `/etc/passwd`, no `/dev/ptmx`, egress through no proxy)
**Relay:** `tcp.ssh.relay.ajam.dev`, version `2026-10-01-r2`, reverse enabled
**Client/tool:** [`dropssh` v0.2.3](https://github.com/talaria0101/dropssh), release `dropssh-x86_64-linux-musl.tar.gz`
**Artefact:** `tools/ssh-relay-check.sh`, which reproduces this note from nothing but the network

This is the "can this host be SSH'd into at all" check that
[`docs/ANONYMOUS-VMS.md`](../../docs/ANONYMOUS-VMS.md) cites. It matters because
the sandbox is a **sealed cage**: `sandhome report` says `bind=unix`, which means
`bind(2)` on `AF_INET` is refused with `EACCES`, and `passwd=no`, which means
there is no `/etc/passwd`. A normal `sshd` cannot start here — the
[`sealed-sandbox` skill](../../.agents) records that OpenSSH in `-i` mode needs a
privilege-separation user and a chroot directory, and neither can be created.

```
dropssh: operator opened session 4d805ba8 (ready sent)
[10318] Child connection from unix:0
[10318] Pubkey auth succeeded for '966' with ssh-ed25519 key SHA256:686ij2Ah... from unix:0
[10318] Exit (966) from <unix:0>: Exited normally
PASS: a real ssh login ran over the outbound-only relay
```

The command run over the session was `id -u` + `uname -s`, and it returned
`966` and `Linux`. Tokens are redacted here and are never echoed by the script.

## What had to be true, and the three attempts it took

**1. The passwd database must come from a file, not the system.** With no
`/etc/passwd`, the first login said `Login attempt with wrong user root`.
`dropssh` ships a dynamic-glibc `dropbear` plus a `fakepwd.so` `LD_PRELOAD`
shim for that case, but the binary in the `v0.2.3` tarball is a static-pie
musl `dropbear`, which cannot be interposed at all. The patch that makes the
static server usable is `-Y FILE`: it reads a `passwd(5)` line per login. With
`-Y ./passwd`, the same login reached `Pubkey auth succeeded`.

**2. The login uid must equal the server's uid.** `dropbear` refuses a login
whose uid differs from the process serving it. The first `-Y` file named
`root:0:0`, and the server (running as uid 966) still answered `Login attempt
with wrong user root`. Rewriting the line as `966:x:966:965:...` fixed it.
This is the same constraint dropssh's own `tests/passwd-file-test.sh` documents.

**3. The server's paths must not sit under a world-writable directory.** With
the work dir under `/tmp`, dropbear logged:

```
/tmp must be owned by user or root, and not writable by group or others
```

`/tmp` is `1777`. Moving the host key, the `-D` authorized-keys directory and
the passwd file under a directory this user owns and can execute (here the
repository's own `.dropssh-check/`) made the login work. The passwd home
directory must also be owned by the login user.

## The relay pair, and why no token is committed

`dropssh pair` calls the relay's self-service rendezvous endpoint
(`POST /v1/pair`) and returns a random 128-bit name, a `node_token`, a
`connect_token` and a `stop_token`, all expiring within 72 h. The relay's own
documentation states the trust model plainly: the relay authenticates tokens,
not people, and the connect token must reach the operator over a trusted
channel (TOFU).

That is a credential, so this repository does not carry one. The script mints a
fresh pair on every run, writes the tokens mode 600 inside `.dropssh-check/`,
and never prints them; a public key is the only key material that is generated
(an operator key, `ak/id`, with `ak/authorized_keys`), and it stays in the work
dir. `gitignore` excludes that directory.

## Reproduce

```sh
sh tools/ssh-relay-check.sh
```

It fetches the pinned release, checks its `SHA256SUMS`, generates a host key and
a login key, writes a passwd entry for the current uid, serves one session, and
connects through the relay with `ssh -o ProxyCommand=...`. Exit 0 means a real
login ran. It does not need `sandhome`; where the client `ssh-keygen`/`ssh`
cannot map the local uid because there is no `/etc/passwd`, it loads the
`sandhome` `fakepwd.so` shim if one is present.

## Scope, stated honestly

- This proves the transport and the login. It does **not** claim the relay is
  private: the name and both tokens are bearer credentials for a maximum 72 h,
  and anyone who reads them can open a session.
- It does not run a server after the check exits. `--once` serves one session
  and the script kills the process; nothing here leaves a listening or dialing
  node behind.
- The relay's forward path (`--mint`) and the public gateways it fronts (for
  example `ssh railway.new`) were not driven from this host as part of this
  note; only the reverse node path above was.
