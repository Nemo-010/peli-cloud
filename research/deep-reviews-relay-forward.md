# Deep reviews: the relay forward transport and colo rotation

Ten passes over `docs/RELAY-FORWARD.md`, `data/relay-colo-egress.json`,
`tools/relay-probe.sh`, `tools/check-relay-egress.py` and
`research/verification/relay-forward-2026-10-02.md`. Each names the question,
the method, what it found, and what changed. Written 2026-10-02.

## R1 — Door sweep: what other route reaches what this pass wrote?

Enumerated every file that reads the new artefacts, then grepped
(`grep -rln 'relay-colo-egress\|relay-probe'`).

| route | reaches | difference |
| --- | --- | --- |
| `tools/relay-probe.sh` | mints a token, probes the 4 colos, writes the JSON | the only producer |
| `tools/check-relay-egress.py` | reads the JSON | asserts invariants; no network |
| `tests/regressions-relay-forward.sh` | the JSON and the guard | mutants + tree clauses |
| `docs/RELAY-FORWARD.md` | the JSON and the manifest | prose |
| `research/verification/relay-forward-2026-10-02.md` | raw trace excerpts | the evidence behind the prose |

**Finding:** the report cites `data/relay-colo-egress.json` as its measured
result, and that file is regenerated by `relay-probe.sh` on every run, so the
committed copy is a point-in-time capture, not a live value. **What changed:**
the report and the verification note both say the numbers are from
2026-10-02T08:16Z and are point-in-time.

## R2 — Guard mutation: can `check-relay-egress.py` actually fail?

The guard asserts four colos, distinct egress IPs inside `104.28.0.0/16`, a
`live` forward verdict, an `SSH-2.0` banner, and `token_required`.

| mutant | setup | expected | got |
| --- | --- | --- | --- |
| duplicate IP | colo 1 egress := colo 0 egress | reject | reject |
| out-of-block IP | colo 0 egress := `203.0.113.7` | reject | reject |
| unmutated | committed JSON | accept | accept |

All three behaved. **What changed:** the two mutant clauses are committed in
`tests/regressions-relay-forward.sh`, so the guard is re-proved on every run
rather than assumed.

**The guard's own limit, stated:** it checks the *shape* of a committed file. It
does not re-fetch, so it cannot tell a fresh measurement from a stale one. That
is what `relay-probe.sh` is for.

## R4 — Attacking the "rotation" claim itself

**Question:** is the egress-IP difference *rotation*, or just four relays that
happen to sit in four places?

**Finding:** the measurement shows four distinct source addresses, one per
colo. It does **not** show that a colo's egress is stable across time, nor that
`?spread=` changes the address within one colo. One probe per colo cannot
establish either. **What changed:** the report states exactly what is shown —
"the source address observed by the target changes with the chosen colo" — and
drops the stronger word "rotating" from any claim the data does not support.

## R5 — Did any committed file leak the caller's address?

**Method:** grep the committed artefacts for the caller's `request.client_ip`,
city, region, ASN and coordinates seen in the raw traces.

**Finding:** none appear. The raw captures (which contain them) are written as
`*.raw` and are now excluded by `.gitignore`; only the manifest, with hashes, is
committed. **What changed:** added `sources/**/*.raw` to `.gitignore` in this
pass (the rule did not exist before), and the verification note says the caller
fields are redacted and why.

## R6 — Attacking the forward-transport claim

**Question:** the report says the forward transport is "confirmed". Is it?

**Finding:** only partly. The banner check uses `/trace?target=...&banner=1`,
which is a **server-side diagnostic**: the Worker dials the target and reports
the result. A real forward session is a client WebSocket to
`/connect/<host>/<port>`. The two share the dial and the road, but they are not
the same code path. **What changed:** the report's limits section now says a
client-driven `/connect` WebSocket was **not** driven in this pass, and the
"confirmed" verdict in the verification note is scoped to "the same target dial
a `/connect` session performs".

## R7 — Attacking the "any public target" policy claim

**Question:** `allow=any public target` — tested?

**Finding:** it is read from the relay's own policy fields, not tested against a
denied case. `deny_ports` is `[]` and `dns_guard` is `true`, so the guard is
DNS-based; a private address or a denied port was not attempted. **What
changed:** the report presents `allow` as a *reported policy value* and lists
"not tested against a denied target" among the things not established.

## R8 — Credential audit

**Question:** is any relay token committed?

**Method:** grep the files this pass writes for a 64-hex run; the regression
test carries the same clause (`no_committed_tokens`).

**Finding:** none. `relay-probe.sh` and `fetch-relay-sources.sh` mint a token
per run, pass it in a header, and never print it. **What changed:** nothing to
fix; the clause is committed so it stays true.

## R9 — Reproducibility

**Method:** run the three scripts from the tree.

- `sh tools/relay-probe.sh` → exit 0, `PASS: 4 colos measured, forward banner live`.
- `sh tools/fetch-relay-sources.sh` → writes the manifest, all six rows 200.
- `sh tests/regressions-relay-forward.sh` → 11 clauses, 0 fail.
- `sh tests/regressions-relay-forward.sh --stash` → the pre-existing-file clause
  (`.gitignore` raw rule) is the one that fails against the pre-fix tree.

**Finding:** all pass. **What changed:** nothing.

## R10 — Standalone check

**Question:** does `docs/RELAY-FORWARD.md` stand on its own?

**Finding:** it defines the transport, the auth, the pool and the measurement
without requiring the chat or another repository. It links to `SSH-RELAY.md`
for the reverse path and to the verification note for raw evidence, but neither
is required to read the forward report. **What changed:** added the explicit
"Related" line and the data/manifest pointers at the top so a reader landing on
the page knows where the evidence is.

## What this pass did not establish

- A client-driven `/connect` WebSocket session (R6).
- Egress-IP stability over time, or `?spread=` within one colo (R4).
- Behaviour against a denied target, a private address or a denied port (R7).
- Throughput, concurrency, or sustained-session behaviour.
- The `direct` egress road (every probe took `vpc`).
- IPv4 egress (every observed egress was family 6).
- That the relay is a source of machines: it is a byte transport. The report
  states this explicitly, because "different egress IP" is not "different VM".
